Authentication

All API requests require authentication via API key/secret and a secure data. Secure data is constructed from walletId and public RSA key provided by us.

API Key Authentication (Server-to-Server)

Include these headers in every request:

Header Description Example
X-Api-Key Provided api key a208c005-17a2-441a-b3e9-58b6e0d6c082
X-Api-Secret Provided api secret 3208c005-17a6-441a-b3e9-58b6e0d6c082
X-Wallet-Id Target wallet identifier 1234567890
X-Secure-Data Encrypted secure data token Base64 string

X-Secure-Data Header Generation

You need to have a walletId and its corresponding RSA public key (accessKey) stored in previous step to generate the X-Secure-Data header for authenticated requests. The X-Secure-Data header contains encrypted wallet authentication data.

1. Data Structure

Create a JSON payload with the following fields:

Field Type Description
deviceId String The wallet ID
timestamp String ISO 8601 format: yyyy-MM-dd'T'HH:mm:ss.SSS'Z'
JSON · Example Payload
{
  "deviceId": "16250953",
  "timestamp": "2023-10-27T10:00:00.123Z"
}

2. Encryption

Encrypt the JSON string using RSA:

Parameter Value
Algorithm RSA
Mode ECB
Padding PKCS1Padding (PKCS#1 v1.5)
Key Wallet's RSA Public Key (X.509 encoded)

3. Encoding

Base64 encode the encrypted byte array.

Example (JavaScript)

JavaScript
const publicKeyPEM = "RSA PUBLIC KEY of walletId 1234567890";
const payload = {
  walletId: "1234567890",
  timestamp: "2026-01-07T09:40:16.524Z"
};
const secureData = await RSA.encrypt(JSON.stringify(payload), publicKeyPEM);

QR Code Transaction Types

Code Description
PAYMENT Standard purchase payment initiated by QR scan
REFUND Refund against an original PAYMENT transaction

QR Code Statuses

Code Description
READ_QR Payment info API was called; QR data received
IN_PROGRESS QR code confirmed; awaiting fund transfer result
FAILED Transaction failed; no funds moved
COMPLETED Transaction successfully completed

QR Code Payment Flow

Payment — Step by Step

1
Read

Partner calls /qrcode/payment/read. Response type is PAYMENT.

2
Amount prompt (open-amount only)

If the returned amount is null, the partner presents an amount entry UI to the user before proceeding.

3
Debit

Partner debits the resolved amount from the customer's account. This happens before calling confirm.

4
Confirm

Partner calls /qrcode/payment/confirm. If the QR was open-amount, the user-entered amount must be included in the request body.

5
Webhook — COMPLETED

Partner notifies the user of success.

6
Webhook — FAILED

Partner reverses the earlier debit and notifies the user of the failure.

QR Code Refund Flow

Refund — Step by Step

1
Read

Partner calls /qrcode/payment/read. Response type is REFUND and always includes a non-null parent_id and a fixed amount.

2
Confirm

Partner calls /qrcode/payment/confirm

3
Webhook — COMPLETED

Partner credits the customer's account and notifies success. The credit must not happen before this event.

4
Webhook — FAILED

No credit is issued. Partner notifies the user of the failure.

Confirm QR Payment

POST /wallet/qrcode/payment/confirm
⚡
For payments, partner debits the resolved amount from the customer's account. This happens before calling confirm. For refunds, partner must wait for the webhook to credit the amount to the customer's account.

Confirm Request Parameters

Parameter Type Required Length Notes
transactionId String Required 255 The unique identifier of the transaction.
tenantReferenceId String Required 100 Tenant's unique reference ID for this transaction.
amount BigDecimal Required - The transaction amount.
tenantUserId String Required 50 The unique identifier of the tenant's user/customer.
tenantName String Optional 50 The name of the tenant user.
tenantSurname String Optional 50 The surname of the tenant user.
tenantNationality String Optional 50 The nationality of the tenant user.
tenantBirthDate String Optional 10 The birth date of the tenant user (e.g. 28-12-1996).

QR Code Webhook

Once finalized, the system sends a POST request to the Partner webhook at /partner/qrcode/webhook. The result of IN_PROGRESS operations will be sent as COMPLETED or FAILED.

Retry Policy

  • Expect 200 OK response
  • Retry up to 3 times with 10-second delay
  • Then retry every hour for up to 48 hours

Headers

Header Description Example
request-sign HmacSHA256 hash of the request body using your secret key 5e884898da28047151d0e56f8dc6292773603d0d6aabbdd62a11ef721d1542d8

Webhook Signature Verification

To ensure the security and integrity of the webhook, PayPorter signs the request body using a secret value.

Secret Value
A secret value, which we will provide, is used during the hashing process. This secret value ensures the security and integrity of the webhook.

Hashing Process
The hash value included in the request is generated by hashing the entire request body using the HmacSHA256 algorithm with the provided secret. This process ensures that the request has not been tampered with.

Request Header
The resulting hashed value is included in the request under the request-sign header.
